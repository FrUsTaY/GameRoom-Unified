Единая экосистема для учёта игр и ведения игрового бэклога с двусторонней распределённой синхронизацией между Android-смартфоном и веб-сервером Game-Room-Web на Ubuntu Server 24.04.

> 📖 **[Полное пошаговое руководство от А до Я читайте в FULL_SETUP_GUIDE.md](FULL_SETUP_GUIDE.md)** (сборка `.apk`, запуск на сервере, настройка Tailscale Funnel и повседневная синхронизация).

## ✨ Ключевые возможности

- 📱 **Offline-First Android клиент:** полноценная работа без интернета, локальная очередь с компактизацией (`sync_queue`), монотонный `client_seq`.
- ⚡ **Двусторонняя синхронизация:** изменения на ПК мгновенно приходят на смартфон, а мобильные правки — на сервер.
- 🛡️ **Разрешение конфликтов LWW (Last-Write-Wins):** устранение перекоса часов через относительное время $\Delta t$, автоматическая доставка побеждающей версии проигравшему клиенту.
- 🗑️ **Надёжное удаление (Tombstones):** таблица `sync_tombstones`, защита от случайного воскрешения удалённых записей устаревшими обновлениями.
- 🔒 **Защита серверных метаданных:** частичные обновления с телефона никогда не затирают богатые метаданные RAWG (жанры, издатели, обложки, Metacritic).
- 🌐 **Работа в Tailscale Funnel:** сервер доступен через публичный HTTPS на порту `:8443`, работая параллельно с уже существующим сайтом на порту `:443`.
- 💾 **StopGame рейтинги:** полная поддержка фирменных SVG-плашек («Изумительно», «Похвально», «Проходняк», «Мусор»).
- ⏱️ **HowLongToBeat (HLTB) Интеграция:** автоматическое получение примерного времени прохождения через выделенный внутренний Node.js микросервис (без необходимости ручной установки Node.js на хосте).
- 📅 **Календарь релизов:** отдельная вкладка веб-интерфейса с помесячным обзором предстоящих и состоявшихся релизов RAWG, фильтрами по платформам/библиотеке и быстрым добавлением игр в бэклог.

## 🚀 Быстрый старт на Ubuntu Server 24.04 LTS

### 1. Перенос на сервер
Скопируйте директорию `server/` на ваш сервер:
```bash
rsync -avz --exclude '__pycache__' --exclude '.git' ./GameRoom-Unified/server/ user@your-server-ip:~/gameroom/
cd ~/gameroom
```

### 2. Запуск Docker контейнеров
```bash
chmod +x deploy.sh
./deploy.sh
```
Docker Compose автоматически соберёт два сервиса (`gameroom-web` и `hltb-service`), смонтирует постоянное хранилище `./data/backlog.db` и поднимет основной веб-сервер на порту `8080`. Отдельная установка Node.js на хосте не требуется!

### 3. Настройка Tailscale Funnel (Порт 8443)
Поскольку порт 443 уже занят вашим первым сайтом, открываем безопасный порт 8443:
```bash
# 1. Привязка порта контейнера к 8443
sudo tailscale serve --bg --https=8443 http://127.0.0.1:8080

# 2. Включение публичного доступа через интернет
sudo tailscale funnel --bg 8443 on

# 3. Проверка статуса
tailscale funnel status
```

Ваш сервер теперь доступен по адресу:  
`https://<ваша-нода>.ts.net:8443`

## 📱 Подключение Android-клиента

1. Откройте в браузере `https://<ваша-нода>.ts.net:8443/` и перейдите в **«Настройки»**.
2. В карточке **«СИНХРОНИЗАЦИЯ С ANDROID (SYNC ENGINE)»** нажмите **«📋 Копировать»** возле `Секретный Sync Token`.
3. Откройте приложение **Game-Room** на Android-смартфоне:
   - Откройте **Настройки** приложения.
   - Вставьте URL сервера: `https://<ваша-нода>.ts.net:8443`
   - Вставьте скопированный токен в поле **Sync Token**.
   - Включите **Автоматическая синхронизация**.
   - Нажмите **«Проверить связь»** (статус сменится на `✅ Связь установлена!`).
   - Нажмите **«⚡ Первичная синхронизация (Initial Sync)»** для объединения существующих баз.

## ⚙️ Правила разрешения конфликтов (Conflict Resolution)

| Ситуация | Правило разрешения | Описание |
| :--- | :--- | :--- |
| **Параллельное редактирование** | **LWW (Last-Write-Wins)** | Сервер рассчитывает относительную разницу времени $\Delta t$, устраняя погрешность часов клиента. Более свежее изменение побеждает. |
| **Проигравший клиент** | **Автоматическая сходимость** | Проигравший клиент получает актуальную победившую запись сервера и обновляет локальное состояние. |
| **Устаревшее удаление (Stale Delete)** | **Update побеждает Delete** | Если клиент удалил игру офлайн, а на сервере она была обновлена позже, удаление отклоняется, а запись возвращается клиенту. |
| **Устаревшее обновление (Stale Update)** | **Tombstone побеждает Update** | Если клиент редактировал игру, которая уже удалена на сервере, игра не воскрешается, а клиенту приходит команда на удаление. |
| **RAWG Метаданные (Категория B)** | **Защита от затирания** | Частичные обновления с мобильного клиента (часы, оценка, заметка) никогда не обнуляют серверные данные RAWG (жанры, разработчик, обложки). |
| **Перенос Wishlist → Games** | **Иммутабельный UUID** | UUID записи остаётся неизменным. Сервер меняет статус на `playing`, дубликат записи не создаётся. |
| **Офлайн-очередь на телефоне** | **Компактизация очереди** | Последовательные действия над одной игрой без интернета схлопываются в единое результирующее действие. |

## 📅 Календарь релизов

Вкладка **«📅 КАЛЕНДАРЬ РЕЛИЗОВ»** в веб-интерфейсе предоставляет помесячный обзор игровых релизов.

**Источник данных:** RAWG API (`/games` с фильтром `dates=ГГГГ-ММ,ГГГГ-Последний_день`). Для работы требуется настроенный `RAWG_API_KEY` (карточка «Настройки API»); без ключа интерфейс корректно показывает приглашение настроить ключ.

**Возможности:**
- Навигация по месяцам (‹ / ›) и возврат к текущему месяцу, поиск релиза по названию;
- Мультиселект чипов по семействам платформ (🖥️ PC, PlayStation, Xbox, Nintendo Switch; по умолчанию — «Все»);
- Фильтр по статусу в библиотеке: `Все игры` / `Уже в библиотеке` / `Не добавлены` / `Хочу пройти` — матчинг релиза с игрой выполняется сначала по `rawg_id`, затем по `slug`, затем по нормализованному названию;
- Быстрое добавление релиза в бэклог через существующий эндпоинт `POST /api/rawg/quick-add` (с серверной защитой от дубликатов) и смена статуса через `PUT /api/games/{id}`;
- Просмотр трейлеров в общем модальном окне `trailer-modal`;
- Серверное кэширование ответа на 6 часов (`CALENDAR_CACHE_TTL_SECONDS`) — данные месяца статичны, повторные запросы бесплатны для квоты RAWG; до 6 страниц (~360 релизов) за месяц с дедупликацией по RAWG id.

**API:**
| Метод | Путь | Описание |
| :--- | :--- | :--- |
| `GET` | `/api/rawg/releases-calendar/{ГГГГ-ММ}` | Список релизов за месяц (например, `2026-10`). Требует авторизацию (`verify_auth`). Формат месяца валидируется на сервере (400 при ошибке). |

Код календаря реализован во фронтенде (`server/static/js/app.js`, методы `loadReleaseCalendar` / `renderReleaseCalendar`) и на сервере (`server/rawg_service.py`, функция `get_releases_calendar`). Синхронизация с Android-клиентом не затрагивается: календарь использует только обычные записи бэклога.

### Обновление фронтенда и Service Worker (после деплоя)

Веб-интерфейс работает как PWA с Service Worker (`server/static/sw.js`). Чтобы после развёртывания новой версии браузер не показывал устаревшие CSS/JS (дефект, из-за которого после PR #6 страница «зацикливалась» до `Ctrl+F5`), действует следующая схема:

- **Единая версия ресурсов — параметр `?v=N`.** При каждом деплое, меняющем статику, нужно синхронно поднять номер в трёх местах: константа `ASSET_VERSION` в `sw.js` (из неё же автоматически формируется имя кэша `gameroom-pwa-vN-auth`) и ссылки `/css/spider_verse.css?v=N`, `/js/app.js?v=N` в `index.html` и `login.html`. Версионированный URL — новый ключ кэша, поэтому старая копия становится недостижимой по дизайну; устаревшие записи вычищаются при активации нового воркера. Сам Service Worker регистрируется из `app.js` также с версионированным URL (`/sw.js?v=N`), что принуждает браузер проверить его байт-за-байтом при обычной загрузке страницы.
- **Политики воркера:** HTML-навигации и `/api/*` обслуживаются **только из сети** (никогда из кэша — это защищает авторизацию и свежие данные); однодоменная статика отдаётся по схеме «кэш + фоновая ревалидация» с проверкой ETag.
- **`sw.js` отдаётся с `Cache-Control: no-cache`**, поэтому браузер проверяет его актуальность при каждой навигации; новая версия SW активируется и перехватывает контроль над клиентами (`clients.claim()`), а страница корректно обновляется по обычной кнопке «Обновить» — без `Ctrl+F5`.
- **HTML сам не кешируется** — достаточно поменять `?v=` в шаблонах, и клиент гарантированно получит новые ссылки.
